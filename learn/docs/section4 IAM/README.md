  - IAMの概要1 - IAM特徴 - AWSアカウント内のIDを作成・管理 - リソースへのアクセス権限をポリシーで制御 - リソース間のアクセスや一時的な権限移譲 - IAMの構成 - IAMアイデンティティ - IAMユーザー - AWSアカウント内に利用される利用ユーザー。

            - IAMグループ
              - グループとしてまとめて権限を付与する仕組み
            - IAMロール
              - AWSリソースが別のリソースに対するアクセス権限を付与する仕組み。別のAWSアカウントのIMAユーザーにアクセス権限を以上する際にも利用。

          - **IAMポリシー**
            - JSON形式
              - ユーザーへのアクセス権限を付与するための設定ドキュメント
            - アクション/リソース
              - Action、Resource(対象リソース)、Effect(Allow/Deny)
            - 条件付きアクセス
              - Condition(定慧itemsん)で絞り込み、より細かいアクセス制御を実現
          - **ポリシー原則**
            - ## 明示的なDenyが最優先
            - スコープはARNで厳密化
            - 条件で絞り込み
          - **ポリシーの設計パターン**
            - 管理ポリシーの再利用
              - 共通の権限を管理ポリシーとして定義し、複数ユーザーに適用
            - 必要箇所だけインライン
              - 特定のリソースに対する細かいインラインポリシーで設定する
          - **IAMポリシーの構成要素**
            - Version
              - ポリシーのVersion
            - Statement
              - ポリシーの主要な記述ロジック
            - Effect
              - 許可/拒否
            - Action
              - 実行可能な操作
            - Resource
              - 対象リソース
            - Condition
              - 条件(オプション)
          - IAMユーザーの種類は省略
            - IAMグループ全体で サービスを許可されていても個人でサービス利用が拒否されていたら、サービスは使えない。理由は、拒否が最優先されるから

  - IAMの概要2
    - IAMロールはAWSリソースに対して一時的なアクセス権限をロールとして付与できる仕組み。
      - EC2、Elastic BEanstalk、Data PiplineなどのAWSサービスがロールを引き受けて、他のリソースにアクセス可能

  - IAM設計
    - セキュリティポリシーとの融合
    - 役割・責務の明確化
    - 最小権限の原則
    - 設計ポイント
      - セキュリティポリシーの統合
      - vue和クリベースのアクセス制御
      - 最小権限の原則
      - 運用の容易性
    - ベストプラクティス
      - ルートなどの特権flaseはMFAを有効か
      - 個別ユーザー発行
        - 利用者ごとに個人ユーザーアカウントを発行する
      - 原則グループ管理
      - PW強度の設定
        - ユーザーのために強度の高いPWポリシーを設定
      - EC2などのロールを使用
        - EC２インスタンスで作動するアプリケーションはロールを使用
      - STSで一時的な認証情報
        - モバイルやアプリケーションはSTSで最小限の利用許可
      - アカウント活動を常時監視

      - グループ設計の推奨方針
        - グループ中心設計のメリット
          - スケーラビリティ: 組織拡大時に新規ユーザーを簡単に追加
          - 異動対応: 役割変更時の権限移行が容易
          - 棚卸し管理: 不要な権限の削除が効率的
          - 監査対応: 権限の可視性・追跡性向上
        - 役割別グループ設計例
          - IT管理者
            運用管理者..
            ............
        - **Point:グループ設計の流れ**
          - 利用者の洗い出し⇨役割整理→グループ集約→権限確定
